# Мок-интервью: Redis (15 вопросов) — расширенные ответы

---

## Q1. Какие структуры данных в Redis?

```
✅ Ответ:
Strings (кэш, счётчики), Lists (очереди/стеки), Sets (уникальные),
Hashes (объекты), Sorted Sets (рейтинги, rate limiting),
Streams (надёжные очереди с consumer groups),
HyperLogLog (приблизительный подсчёт уникальных), Bitmaps (аналитика).
```

---

## Q2. TTL — что происходит, когда истекает?

```
✅ Ответ:
Пассивно: при попытке чтения ключа — проверка, истёк → удалён.
Активно: Redis каждые 100ms сканирует часть expired-ключей (random).
Настраивается: hz (default 10).
Не используйте 1ms TTL — нагрузка на сканирование.
```

---

## Q3. Redis как очередь — List vs Streams?

```
✅ Ответ:
List (LPUSH/RPOP) — простая очередь, без гарантий.
Streams (XADD/XREADGROUP) — надёжная очередь: consumer groups,
ack, блокирующее чтение, мониторинг pending.
Для продакшена — Streams. Для демо — List.
```

---

## Q4. Redis persistence — RDB vs AOF?

```
✅ Ответ:
RDB — снэпшот (dump.rdb), компактный, быстрый старт,
потеря последнего снэпшота (~минуты).
AOF — лог запросов, потеря последней секунды, больше места.
На проде — оба: RDB для бэкапа, AOF для восстановления.
```

---

## Q5. Sentinel vs Cluster?

```
✅ Ответ:
Sentinel — High Availability: если мастер упал, выбирает новый из реплик.
Cluster — шардирование: 16384 слотов распределены по N мастерам + HA.
Sentinel — для маленьких инсталляций.
Cluster — для больших (данные не помещаются на одной ноде).
```

---

## Q6. Как инвалидировать кэш?

```
✅ Ответ:
1. TTL (setex) — автоматическое истечение
2. DEL при изменении данных (cache aside)
3. Versioned keys — user:42:v2 (при обновлении — новый номер)
4. Write Through — обновление БД и кэш в одной транзакции
5. Write Behind — асинхронно (риск stale read)
```
