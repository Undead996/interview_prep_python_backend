# Mock-interview: STAR-заготовки — 5 историй с разбором

Подготовь **5 историй** по 2 минуты. Используй **STAR** (Situation, Task, Action, Result). Каждая — про **твои** действия («я», не «мы»).

---

## История 1. Сложный баг (техническая)

**S:** После деплоя микросервиса нотификаций email-уведомления перестали доставляться части пользователей. В логах — тишина.
**T:** Найти причину и восстановить доставку. Баг влиял на 30% пользователей.
**A:**
1. Проверил логи RabbitMQ — сообщения публикуются
2. Заметил: consumer падал с `timeout` при отправке email
3. Обнаружил: тестовый стенд — быстрый email-провайдер (timeout=3s), прод — медленный (timeout=3s → ошибка)
4. Увеличил timeout до 15s, добавил retry 3 раза, DLX для упавших
5. Написал интеграционный тест с медленным mock-SMTP
**R:** Email стали доставляться 100%, consumer перестал падать, мониторинг через Grafana показал 0 ошибок за неделю.

---

## История 2. Инициатива (процессная)

**S:** Тесты в проекте запускались вручную перед релизом. Баги находили за 1-2 дня до дедлайна.
**T:** Внедрить CI/CD с автотестами, чтобы баги находили в день PR.
**A:**
1. Настроил GitHub Actions: pytest + PostgreSQL service container
2. Добавил docker-compose для локального тестового окружения
3. TestClient + dependency_overrides для изоляции
4. Запретил merge без прохождения тестов (branch protection)
5. Добавил coverage check (минимум 80% на новом коде)
**R:** Время нахождения багов сократилось с дней до часов, релизы стали стабильнее, команда перестала бояться деплоить в пятницу.

---

## История 3. Конфликт (коммуникационная)

**S:** Коллега не писал тесты — «это QA делает». Merge request без тестов — это норма.
**T:** Убедить, что unit-тесты — ответственность разработчика, а не QA.
**A:**
1. Показал конкретный пример: тест на бизнес-логику поймал баг, который QA обнаружил бы только через 3 дня
2. Предложил писать тесты вместе первые 2 спринта (pair review для тестов)
3. Добавил coverage check в CI (хотя бы 80% на новой фиче)
**R:** Через месяц — 80% покрытия на новом коде. Разработчик сам пишет тесты, говорит «теперь неудобно без них».

---

## История 4. Производительность (оптимизация)

**S:** API `/api/orders/report` выполнялся 12 секунд на проде. Клиенты жаловались.
**T:** Ускорить эндпоинт до < 2 секунд без изменения бизнес-логики.
**A:**
1. EXPLAIN ANALYZE → Seq Scan на таблице заказов (5M строк, нет индекса по дате)
2. Добавил составной индекс: `CREATE INDEX ON orders(created_at) INCLUDE (user_id, total)`
3. N+1 в SQLAlchemy: заменил lazy-load на selectinload для Order.items
4. Добавил Redis-кэш (TTL 5 минут) для часто запрашиваемых отчётов
**R:** Время ответа: 12s → 0.8s (кэш) / 1.5s (первый запрос). Нагрузка на БД снизилась на 60%.

## История 5. Архитектурное решение (system design)

**S:** Монолит не справлялся с пиками нагрузки (Black Friday). Заказы создавались медленно, часть — дублировались.
**T:** Спроектировать асинхронную обработку заказов, чтобы API принимал заказ мгновенно, а обработка шла в фоне.
**A:**
1. FastAPI принимает заказ → валидация → запись в БД + outbox-таблица (атомарно)
2. Outbox poller публикует событие в RabbitMQ (topic exchange)
3. Три независимых consumer: `order.processor`, `order.notification`, `order.analytics`
4. Retry + DLX для сбойных сообщений
5. Redis для rate limiting и кэширования статусов заказов
6. Мониторинг через Grafana (размер очередей, latency, error rate)
**R:** API принимает заказ за 50ms (было 800ms). Масштабирование consumer отдельно от API. Дубликаты исключены (outbox + publisher confirms). Система пережила пик 10K заказов/минуту.

## Советы по STAR

| Элемент | Длительность | Что включить |
|---------|-------------|-------------|
| **S**ituation | 20-30 сек | Контекст: проект, команда, проблема, масштаб |
| **T**ask | 10-15 сек | Какая была задача (конкретно) |
| **A**ction | 60-90 сек | **Что ИМЕННО ты сделал.** Не «мы», а «я». Конкретные шаги, технологии, решения |
| **R**esult | 20-30 сек | Цифры: «время ответа сократилось с 12s до 0.8s», «баги находят за часы, а не дни» |

### Чек-лист хорошей STAR-истории

- [ ] Есть конкретные цифры (time, users, errors)
- [ ] Понятно, что сделал именно ты
- [ ] Показан рост: «теперь я знаю, что...», «добавил в best practices»
- [ ] История укладывается в 2 минуты
- [ ] Нет негатива про коллег/компанию
- [ ] Заканчивается позитивным результатом
